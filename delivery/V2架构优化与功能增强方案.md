## 摘要

本方案在 Vorzai 现有能力基座上（68 张表、15 组 API 路由、17 个前端页面、161/161 测试通过、CALM 式对话引擎、OGSM/RACI/激励/HR 模块、7 平台适配器、跨境/直播行业场景），围绕**采购、销售、运营、人力全链路端到端闭环**与**AI 深度重构业务链**两大主线，提出六大核心引擎设计与落地路线图，将 Vorzai 从"业务骨架 + HR 内核"演进为**对标并超越市场同类产品的电商业务工作台**。

## 一、评审委员会组建

### 1.1 委员会构成

| 角色 | 定位 | 本方案中的评审焦点 |
|---|---|---|
| **工作台搭建师**（组长/主理人） | 个人/团队数字工作台体验专家 | 六大引擎的可用性、双端适配、数据闭环、模块边界 |

| **中国电商运营专家** | 国内平台特性：库存/售后/大促/转化 | 采购供应链、库存攻坚、客户转化、运营链路 |
| **跨境电商专家** | 跨境全链路：到岸成本/合规/多币种 | 供应链协同的跨境侧、汇率/关税联动 |
| **直播电商教练** | 直播场景：开播前中后、复盘 | AI 工作流在直播场景的编排、实时洞察 |
| **数据分析专家** | 指标口径、可验证性、一票否决权 | 实时洞察口径、预测模型、监控面板指标 |

### 1.2 评审机制（沿用 R2 章程）

- 交叉评审：任一引擎必须由至少一名非本域专家复核
- 证据主义：任何结论附 文件:行号 或 验证命令+输出
- 数据专家对指标口径拥有一票否决权
- 共享文件（schema.sql / app.ts / businessService.ts / client.ts / Sidebar.tsx）由组长统一落笔

## 二、现状诊断（基于 2026-08-03 全量代码调研）

### 2.1 能力地图（已有 vs 缺失）

| 业务域 | 已有能力 | 明显缺失 |
|---|---|---|
| **采购** | 仅 `supplierName` 字段 | 供应商台账、采购单、到货/质检、采购成本核算、缺货联动 |
| **销售** | 订单 9 态状态机、收款/退款、组盘、投流、评价 | 售后完整闭环（退货入库/退款时效）、报价/合同 |
| **运营** | 库存预警 5 类规则+归因、大促、活动、平台适配 7 家 | 库存只预警不联动采购、无仓储出入库流水、无自动补货单 |
| **人力** | 员工/考勤/绩效/薪酬/人效后端全有，OGSM/RACI/激励 | **前端 hrStore(IndexedDB) 与后端 hrService 双轨脱节**、无组织架构树、HR 战略分析弱 |
| **AI** | CALM 式对话引擎（11 工具）、chat+dialog 双套 | **chat 与 dialog 并存重复**、RAG 未接入 LLM、无流式、无多 Agent 编排 |
| **数据** | 分析 7 指标/趋势/漏斗/7 维拆解/ABC/客户/健康度、驾驶舱 | 无预测预警、无实时推送、业务线筛选未联动数据 |

### 2.2 三大断层（本次方案必须修复）

1. **HR 前后端双轨脱节**：HRMS 前端 13 个 tab 数据全部来自 hrStore（IndexedDB 本地），未接后端 `/hr` 路由 —— 真实计算（薪酬/考勤/人效）后端已实现但前端看不到。
2. **对话双套并存 + RAG 断裂**：`chat.ts` 与 `dialog.ts` 两套对话系统重复建设；`knowledgeService.searchKnowledge` 已实现但 LLM RAG 问答链路未接通；`parseOrderItems` 用名称占位 productId，AI 下单不可用。
3. **采购/仓储/售后闭环缺失**：业务链在"订单→客服"后断裂，无供应商→采购→入库→出库→退供的供应链闭环。

### 2.3 对标差距（钉钉/飞书/北森/Dify/Rasa）

| 能力 | 市场标杆 | Vorzai 现状 | 差距 |
|---|---|---|---|
| 智能工作流编排 | Dify Workflow / 钉钉流编排 | CALM 单工具串行 | 无可视化编排、无多 Agent 并行 |
| 实时业务洞察 | 飞书/钉钉 BI | 快照式聚合 | 无流式推送、无目标达成实时对标 |
| AI 协同决策 | 北森 AI HR / 钉钉 AI | 单轮工具调用 | 无决策建议生成、无 RAG 增强 |
| 个性化 HR | 北森行业模板 | 通用 HR 计算 | 无行业/场景/规模差异化配置 |

## 三、总体架构优化蓝图

### 3.1 架构演进原则（沿用 R2 硬约束）

- ✅ 不重构不换栈：Electron + React + Express + SQLite（node:sqlite）
- ✅ 向后兼容：既有 API 只增不改不删；数据库只加表加列
- ✅ 零新依赖：图表/图标全内联 SVG，不引外部框架
- ✅ 多租户隔离：新增 SQL 全部带 tenant_id
- ✅ 离线优先：外部数据三选一（手工/导入/沙箱标记）
- ✅ 四件套齐备：新功能 = 后端 service + 路由 + 前端入口 + 数据写入方

### 3.2 六引擎总体架构

```
┌─────────────────────────────────────────────────────────────┐
│                    接入层（触点）                            │
│  智能助手对话台 │ 业务驾驶舱 │ OGSM 看板 │ HR 工作台 │ 移动适配 │
├─────────────────────────────────────────────────────────────┤
│                  业务能力层（六大引擎）                      │
│  ① AI 对话工作流框架   ② 差异化 HR 智能模块   ③ OGSM 追踪体系 │
│  ④ 激励机制引擎       ⑤ 责任人矩阵系统       ⑥ 执行监控面板   │
├─────────────────────────────────────────────────────────────┤
│                  业务链闭环（采购→销售→运营→人力）           │
│  采购供应链 → 库存联动 → 订单销售 → 售后客服 → 人效归因      │
├─────────────────────────────────────────────────────────────┤
│                  基础能力层（复用底座）                      │
│  LLM 工厂 │ RBAC+ABAC 多租户 │ moduleBus │ file-io │ SQLite   │
└─────────────────────────────────────────────────────────────┘
```

## 四、核心设计一：AI 对话工作流框架

### 4.1 目标

统一对话入口，从"单轮工具调用"升级为"流式 + 多轮 + RAG + 可视化工作流编排"的 AI 工作流框架，对话可驱动 ≥15 类高频操作。

### 4.2 架构

```
用户输入
  → 意图路由（LLM 意图 + 关键词降级双保险，复用 dialogEngine）
  → 上下文管理（对话历史 + 业务上下文 + 工具状态）
  → RAG 检索（knowledgeService.searchKnowledge 接入，知识增强回复）
  → 工作流编排（Workflow Engine：节点 = 工具/条件/人工确认）
  → 工具执行（扩展至 15+ 工具：下单/补货/工单/结算/人效/激励...）
  → 流式回复（SSE 流式输出，P99 首字 ≤3s）
```

### 4.3 关键改造点

| # | 改造 | 现状 | 方案 |
|---|---|---|---|
| W1 | 对话入口统一 | chat.ts 与 dialog.ts 双套 | 以 dialog.ts 为主，chat.ts 保留兼容壳（不删端点），前端统一走 `/api/dialog` |
| W2 | RAG 接入 | searchKnowledge 未接 LLM | dialogEngine 工具调度前先检索知识库，命中即注入 system prompt 增强回复 |
| W3 | 流式输出 | 无 | 新增 `POST /api/dialog/stream`（SSE），前端 EventSource 逐字渲染 |
| W4 | 下单可用性 | parseOrderItems 名称占位 | 工具参数改为结构化 schema（productId+quantity），LLM 意图解析直接输出结构化参数 |
| W5 | 可视化工作流 | 无 | 新增 `workflows` 表 + `/api/workflows` CRUD + 前端 WorkflowStudio（节点拖拽 = 内联 SVG 连线） |
| W6 | 多 Agent 分工 | 单引擎 | 按业务线注册 5 个场景 Agent（采购/销售/客服/HR/跨境），共享工具注册表 |

### 4.4 新增表

```sql
CREATE TABLE IF NOT EXISTS workflows (
  id TEXT PRIMARY KEY, tenant_id TEXT NOT NULL, name TEXT NOT NULL,
  description TEXT, nodes TEXT,  -- JSON: [{id,type(trigger/action/condition/human_confirm),tool,params}]
  edges TEXT,                    -- JSON: [{from,to}]
  status TEXT DEFAULT 'draft',   -- draft | active | archived
  created_by TEXT, created_at TEXT DEFAULT (datetime('now','+0000')), updated_at TEXT
);
```

### 4.5 验收

- 对话驱动操作 ≥15 类（现 11 类）
- 流式首字 P99 ≤ 3s；RAG 命中率（知识问答）≥ 70%
- 与既有 51 项冒烟用例全兼容

## 五、核心设计二：基于行业/场景/规模的差异化 HR 智能模块

### 5.1 目标

修复 HR 前后端双轨脱节，将 HR 从"通用计算"升级为**按电商行业、业务场景、企业规模三维差异化**的智能模块，显著提升 HR 战略价值（人效/成本/留存/激励）。

### 5.2 三维差异化模型

| 维度 | 差异化因子 | 落地方式 |
|---|---|---|
| **行业**（电商） | 大促节奏、直播排班、客服三班倒、跨境时差 | 行业日历模板（618/双11/黑五）、班次模板 |
| **场景** | 一线运营/客服/主播/跨境运营/HR 五类岗位 | 岗位绩效模型库（KPI 模板 + 权重预设） |
| **规模** | 微型(<10人)/小型(10-100)/中型(100-1000) | 组织架构复杂度、审批链长度、激励额度档位 |

### 5.3 关键改造点

| # | 改造 | 现状 | 方案 |
|---|---|---|---|
| H1 | **前后端打通（最高优先）** | HRMS 前端用 hrStore(IndexedDB)，后端 hrService 空转 | hrStore 改为后端数据源（api.hr.*），IndexedDB 仅作离线缓存；新增 `hr/sync` 端点做全量拉取 |
| H2 | 组织架构树 | 无 | 部门表已有 parent_id，新增 `/hr/org-tree` 返回嵌套树 + 前端组织树视图 |
| H3 | 岗位绩效模型库 | 绩效权重硬编码（40/25/20/15） | 新增 `hr_job_models` 表：岗位→维度权重→指标模板→评分等级 |
| H4 | 行业日历 | 无 | 新增 `hr_calendars` 表：大促/直播/跨境时差日程，考勤与排班联动 |
| H5 | 离职风险模型 | 驾驶舱硬编码启发式 | 基于考勤异常+绩效下滑+加班超限的规则评分（离线可算），写入效率指标 |
| H6 | HR 战略分析 | 人效/成本静态 | 新增"HR 战略看板"：人效趋势、成本占比、留存率、招聘转化、激励 ROI |

### 5.4 新增表

```sql
CREATE TABLE IF NOT EXISTS hr_job_models (
  id TEXT PRIMARY KEY, tenant_id TEXT NOT NULL, job_category TEXT NOT NULL,  -- operator/cs/live/crossborder/hr
  dimension_weights TEXT,  -- JSON {achievement:0.4,...}
  kpi_template TEXT, rating_scale TEXT, is_sandbox INTEGER DEFAULT 0,
  created_at TEXT DEFAULT (datetime('now','+0000'))
);
CREATE TABLE IF NOT EXISTS hr_calendars (
  id TEXT PRIMARY KEY, tenant_id TEXT NOT NULL, name TEXT NOT NULL,
  calendar_type TEXT,  -- campaign/livestream/shift/crossborder_timezone
  start_date TEXT, end_date TEXT, payload TEXT, is_sandbox INTEGER DEFAULT 0
);
```

### 5.5 验收

- HRMS 前端 ≥80% 数据来自后端 API（证据：接口调用日志）
- 薪酬/考勤计算准确率 ≥99%（既有后端已实现，前端接通后验证）
- 五类岗位各有差异化绩效模型

## 六、核心设计三：目标管理（OGSM）追踪体系

### 6.1 目标

在既有 OGSM 四层闭环（目标→指标→策略→措施）+ RACI + 激励基础上，补齐**目标树可视化编辑、时间序列追踪、目标-经营数据自动对标**三大能力，实现"目标进度实时可见、偏离自动预警"。

### 6.2 关键改造点

| # | 改造 | 现状 | 方案 |
|---|---|---|---|
| O1 | 目标树编辑 | OGSMBoard 只读统计；编辑在 HRMS subviews | 统一 OGSM 目标树组件（拖拽排序、权重设置、折叠），供两处复用 |
| O2 | 时间序列追踪 | 只有快照进度 | 新增 `ogsm_progress_snapshots` 表，每目标每日/每周自动打点（cron 或打开时补点）→ 前端折线图（内联 SVG） |
| O3 | 目标-经营对标 | 无 | `/ogsm/:id/link-metrics`：目标指标关联 analytics 指标口径，实时拉取 GMV/转化等实际值自动填充 current_value |
| O4 | 偏离预警 | 无 | progress < 计划线 80% → 生成 OGSM 偏离告警，进执行监控面板 + 通知中心 |
| O5 | 对齐率增强 | 有 averageAlignment | 增加"公司→部门→个人"三级对齐热力图（SVG 矩阵） |

### 6.3 新增表

```sql
CREATE TABLE IF NOT EXISTS ogsm_progress_snapshots (
  id TEXT PRIMARY KEY, tenant_id TEXT NOT NULL, objective_id TEXT NOT NULL,
  snapshot_date TEXT NOT NULL, progress INTEGER, alignment INTEGER,
  UNIQUE(objective_id, snapshot_date)
);
```

### 6.4 验收

- 目标进度时间线可回看 ≥90 天
- 偏离预警触发准确（对照测试用例）
- 指标自动对标覆盖 GMV/订单/毛利/转化 4 类口径

## 七、核心设计四：激励机制引擎

### 7.1 目标

从"激励登记"升级为**规则驱动、自动计算、闭环发放**的激励引擎：支持业绩提成/团队奖金/专项激励/积分激励四类规则，与 OGSM 目标、订单业绩、人效指标自动联动。

### 7.2 关键改造点

| # | 改造 | 现状 | 方案 |
|---|---|---|---|
| I1 | 规则引擎 | incentives 仅存 rules JSON，无执行 | 新增 `incentive_rules` 结构化表：rule_type(commission/bonus/special/points)、触发条件、计算式（支持 ${metric} 占位符）、上限/下限 |
| I2 | 自动计算 | 无 | `/incentives/calc/:period` 按规则遍历订单业绩/目标达成 → 生成激励记录（incentive_records）→ pending 状态 |
| I3 | 审批流 | 有 pending/approved/paid 状态 | 新增审批动作端点 `/incentives/records/:id/approve|reject|pay`，审计留痕 |
| I4 | 心理激励 | 无 | 新增积分商城（积分兑换奖励配置）+ 成就徽章（SVG 徽章墙，达标自动点亮） |
| I5 | 激励 ROI | 无 | 激励投入 vs 业绩增量对比（激励期间的 GMV 环比），写入 HR 战略看板 |

### 7.3 新增表

```sql
CREATE TABLE IF NOT EXISTS incentive_rules (
  id TEXT PRIMARY KEY, tenant_id TEXT NOT NULL, name TEXT NOT NULL,
  rule_type TEXT NOT NULL,  -- commission | bonus | special | points
  condition TEXT,           -- JSON 触发条件 {metric,op,value}
  formula TEXT,             -- 计算式如 "{gmv} * 0.01 + {bonus}"
  min_amount REAL, max_amount REAL, currency TEXT DEFAULT 'CNY',
  target_type TEXT, target_id TEXT, status TEXT DEFAULT 'active',
  created_by TEXT, created_at TEXT DEFAULT (datetime('now','+0000'))
);
```

### 7.4 验收

- 四类规则均可配置并自动结算（示例数据验证）
- 审批流 4 状态闭环可走通
- 激励计算与订单业绩数据一致（口径审计）

## 八、核心设计五：责任人矩阵系统

### 8.1 目标

在既有 RACI 矩阵（entity→user→R/A/C/I）基础上，补齐**冲突检测、负载均衡、跨层对齐、任务关联**四能力，让"每件事都有唯一 A、责任不真空"。

### 8.2 关键改造点

| # | 改造 | 现状 | 方案 |
|---|---|---|---|
| R1 | A 唯一性校验 | 无 | `setRaci` 校验：同 entity 若已有 A，需先解除或确认替换（返回警告） |
| R2 | 覆盖度检查 | 有 raciCoverage | 新增"无主目标"清单：无 A 且无 R 的目标/任务，在执行监控面板置顶 |
| R3 | 负载均衡 | 无 | `/raci/load`：统计每人 A/R 数量 + 目标数，超阈值标红（A≥5 或 R≥10 预警） |
| R4 | 任务关联 | RACI 只挂目标/指标 | 扩展 entity_type 支持 ticket/project/campaign，客服工单/项目/活动均可挂责任人 |
| R5 | 跨层对齐 | 无 | 公司目标 RACI → 部门 → 个人三级联动视图，展示"我承接了哪些上层目标" |

### 8.3 验收

- 无主目标清单可一键生成
- A 唯一性冲突拦截生效
- 每人负载视图可查、超阈值预警

## 九、核心设计六：落地执行监控面板

### 9.1 目标

一个入口看全盘：**目标执行、业务健康、异常告警、人效归因、激励兑现**五类信息实时聚合，支持"今天要处理"置顶与主动推送。

### 9.2 面板结构

```
执行监控面板（/execution-monitor）
├── 今日要处理（置顶）  逾期目标/缺货预警/无主任务/待审批激励/离职风险
├── 目标执行趋势        公司→部门→个人 OGSM 完成率 + 偏离告警列表
├── 业务健康度          6 维评分 + 库存预警 + 转化漏斗断点
├── 人效与成本          人效趋势/成本占比/HR 战略指标
├── 激励兑现看板        待审批/已发放/积分排行
└── 审计与留痕          关键操作审计（现有 audit_logs）
```

### 9.3 关键改造点

| # | 改造 | 现状 | 方案 |
|---|---|---|---|
| M1 | 聚合接口 | 各域分散 | 新增 `/api/monitor/overview` 一次聚合五类数据（复用各 service） |
| M2 | 异常主动推送 | 有 notifications 表 | monitor 引擎扫描 6 类异常（逾期/断货/偏离/无主/待批/风险）写入 notifications + 面板红点 |
| M3 | 业务线联动 | Sidebar 筛选是 local state | 业务线筛选写入 appStore，monitor/analytics/cockpit 按业务线过滤 |
| M4 | 移动适配 | 桌面优先 | 面板响应式（<768px 单列），关键操作按钮 ≥44px |
| M5 | 数据导出 | 有 CSV 工具 | 监控面板一键导出周报（汇总 + 明细） |

### 9.4 验收

- 五类信息一屏聚合、无需跳转
- 6 类异常主动告警可触发、可关闭
- 周报导出含目标/业务/人效/激励四节

## 十、电商全链路增强（采购 → 销售 → 运营 → 人力）

### 10.1 采购与供应链协同（补最大缺口）

| # | 能力 | 方案 |
|---|---|---|
| S1 | 供应商台账 | 新增 `suppliers` 表（名称/等级/账期/联系方式/评分）+ CRUD + CSV 导入 |
| S2 | 采购单 | 新增 `purchase_orders`（供应商/商品/数量/单价/状态机 draft→submitted→approved→receiving→completed）+ `purchase_items` |
| S3 | 入库质检 | 新增 `stock_transactions`（出入库流水：purchase/sale/return/adjust/transfer），到货入库自动加库存 |
| S4 | 库存联动采购 | inventoryService 断货预警 → 一键生成采购建议单（按补货建议=日均×30−库存），人工确认后转采购单 |
| S5 | 采购成本核算 | 结算/毛利计算纳入采购价（替代硬编码 5% 平台费部分场景） |
| S6 | 供应链协同 | 供应商交期/到货率统计，评估供应商等级；跨境侧联动汇率/关税 |

### 10.2 销售与客户转化

| # | 能力 | 方案 |
|---|---|---|
| C1 | 售后闭环 | 售后工单 → 退货审批 → 退货入库（stock_transactions）+ 退款记录联动 |
| C2 | 转化断点定位 | 复用 analytics 漏斗 6 段，新增"断点行动建议"（AI 生成：如支付页流失 → 建议优惠券） |
| C3 | 客户分层运营 | 复用客户分析（新老/复购/分层），新增客户标签 + 定向营销建议（AI） |

### 10.3 数据与 AI 基础设施

- 指标口径：沿用"revenue=paid_amount>0?paid:total"，新增指标全部带 formula + 口径说明（满足数据可信度）
- 预测预警：基于历史趋势的简单线性预测（离线可算）→ 库存/销售预警增强
- 全量审计：关键操作（采购审批/激励审批/收款）写入 audit_logs
