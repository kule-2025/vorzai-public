## 三、组长统一修复的三处系统性断点

这三处都属于**共享文件**，由组长统一改动，避免多专家并行冲突。

### 断点 1：zod 类型垫片残缺（编译层）

`server/src/types/zod-shim.d.ts` 缺少 20 余个链式方法声明，导致 crossborder / livestream 等模块 **23 处编译错误**。

补全内容：`ZodString` 增补 email/url/uuid/datetime/regex/trim 等 20 项；`ZodNumber` 增补 int/gt/gte/positive/multipleOf 等 18 项；`z.enum` 支持 `readonly`（配合 `as const`）；`z.coerce` 由错误的函数声明改为对象声明。

**结果：编译错误 23 → 3。**

### 断点 2：`db.run()` 返回 unknown（编译层）

新增 `DBRunResult` 接口，`DBStatement.run` 返回类型由 `unknown` 改为结构化类型，消除各处 `as { changes?: number }` 强制断言。

**结果：编译错误 3 → 0。**

### 断点 3：业务数据链路的两个"无写入方"字段（业务层，影响最大）

这是本轮最关键的发现 —— 两个字段全系统**没有任何写入路径**，导致下游指标恒为 0：

| 字段 | 问题 | 修复 |
|---|---|---|
| `orders.owner_employee_id` | 无写入方 → 人效归因恒为空 | `createOrder` 新增 `operatorUserId` 参数与 `resolveOwnerEmployeeId()`：显式指定优先（带跨租户校验），否则按操作人反查 `employees.user_id` 自动解析；无员工档案则落 null 不阻断 |
| `orders.paid_amount` / `payment_status` | **无任何接口能标记订单已支付**，而 GMV/毛利/人效口径均为 `SUM(paid_amount) WHERE 已支付` → 全系统营收指标恒为 0 | 新增 `businessService.recordPayment()` 与 `PUT /api/business/orders/:id/payment`：支持收款/退款（正负金额），支付状态由金额自动推导杜绝口径漂移，结清时自动推进订单状态 pending→confirmed，含超额守恒校验与跨租户防护 |

## 四、端到端验收证据

### 验收方式

启动真实 HTTP 服务（全新 SQLite 库，164 条 schema 语句 0 跳过），脚本 `scripts/smoke-p0.mjs` 走完整业务流：
注册租户 → 鉴权 → 建商品 → 下单 → 分段收款 → 触达全部五大模块端点。

判定标准从严：**非 200 一律计为失败**（而非"接口存在即通过"）。

### 关键结果：51 PASS / 0 FAIL

**支付链路（本轮新修）**

```
创建订单            → 初始 unpaid / pending          PASS
部分收款 80         → paid=80  status=partial        PASS
结清 120            → paid=200 status=paid
                      订单自动 confirmed              PASS
超额收款 +50        → HTTP 400「实收金额 250 超出订单总额 200」PASS
跨租户支付          → HTTP 404 拒绝（安全红线）       PASS
```

**Analytics 真算而非 Mock 的硬证明**

```
gmv=200  orders=1  aov=200  gross_profit=80
gross_margin_rate=0.4  conversion=1  active_sku=1
```

数据完全吻合真实录入：售价 100 × 2 件 = GMV 200；成本 60 × 2 = 120；毛利 80；毛利率 0.4。
**同一套代码在支付登记前返回 gmv=0，登记后返回 gmv=200** —— 这证明它读的是真实库表而非硬编码。

**安全红线**

- 未携带 token 访问受保护端点 → 401
- 跨租户操作他人订单 → 404（不泄露资源存在性）
- 所有查询强制 `tenant_id` 过滤

## 六、收款登记 UI 入口（闭环补齐）

后端 `recordPayment` 落地后，前端仍无任何调用点 —— 用户在界面下单后无法登记收款，
`paid_amount` 在真实使用路径下依然恒为 0，经营分析仍然全零。等于后端白修。本轮补齐：

| 位置 | 内容 |
|---|---|
| `src/api/client.ts` | 新增 `recordOrderPayment(id, { amount, paymentMethod, remark })` |
| `src/views/Modules/BusinessChain.tsx` | 订单详情弹窗内新增「收款登记」面板 |

面板能力：
- 实时展示 **已收 / 待收** 金额
- 正数收款、负数退款，同一入口
- 「结清」按钮一键填入剩余待收金额
- 支付方式下拉：支付宝 / 微信 / 银行转账 / 货到付款 / 其他
- 后端拦截的超额收款、超额退款错误在面板内回显
- 提交成功后同步刷新弹窗与列表行，付款状态徽标即时更新

口径说明直接写在面板下方，避免使用者误解：付款状态由累计实收自动推导，结清后订单
自动由「待确认」推进为「已确认」，经营分析的营收与毛利只统计已收款金额。
