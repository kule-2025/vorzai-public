# Vorzai 多角色开发及评测委员会 — 章程与评测标准

> 版本 v1.0 ｜ 建立于 2026-07-31 ｜ 适用于本轮全量开发与增强（代号 **R2**）

---

## 一、委员会角色分工

委员会由 1 名组长与 5 个专家角色构成。每个角色在**四个环节**均有明确职责，
不允许"只评审不担责"或"只开发不评审"。

| 角色 | 需求评审 | 方案设计 | 开发实施 | 测试验收 |
|---|---|---|---|---|
| **组长（Team Lead）** | 汇总去重、定优先级、裁决冲突 | 统一架构约束、划定模块边界 | 修改共享文件、解决集成冲突 | 终审、回归、发版把关 |
| **经营总管专家团** | 从老板视角判定"值不值得做" | 目标—指标—行动的闭环设计 | OGSM／驾驶舱／人效域 | 验收经营闭环是否可指导决策 |
| **跨境电商专家** | 判定跨境功能的实操可行性 | 到岸成本模型、合规规则集 | 跨境域（crossborder） | 用真实跨境场景走查 |
| **直播电商教练** | 判定直播功能是否贴合现场 | 时序数据结构、复盘维度 | 直播域（livestream） | 用真实开播流程走查 |
| **中国电商运营专家** | 判定国内平台特性覆盖度 | 库存策略、售后与大促模型 | 库存／平台／商品／售后域 | 用真实运营动作走查 |
| **数据分析专家** | 判定指标口径与可验证性 | 口径定义、聚合与快照方案 | Analytics 域、口径统一 | 数据可信度审计、性能压测 |

### 关键机制

1. **交叉评审（Cross Review）**
   任何一个专家提交的功能，必须由**至少一名非本域专家**复核。
   数据分析专家对**所有**涉及指标计算的改动拥有一票否决权（口径不合格即打回）。

2. **共享文件由组长统一修改**
   `businessService.ts`、`app.ts`、`schema.sql`、`client.ts`、`index.ts` 等多方共用文件，
   专家只提需求，由组长落笔，避免并行写冲突。

3. **证据主义**
   任何问题上报必须附 `文件:行号`；任何功能声称完成必须附可复现的验证命令与输出。
   无证据的结论一律不进清单。

4. **禁止复读**
   评审不得引用历史报告结论，必须基于当前代码重新取证。

## 二、预设业务目标（North Star）

所有开发项必须挂靠到下列目标之一，无法挂靠的一律不做。

| 代号 | 业务目标 | 量化定义 | 主责角色 |
|---|---|---|---|
| **G1** | 提升转化率 | 让运营能定位转化漏斗断点并采取行动 | 国内运营 + 数据 |
| **G2** | 扩大跨境业务规模 | 跨境选品到结算全链路可算清利润、不踩合规红线 | 跨境 |
| **G3** | 优化运营效率 | 减少人工重复操作、异常能主动推送而非被动查询 | 经营总管 + 国内运营 |
| **G4** | 提高数据可信度 | 指标口径唯一、可追溯、可下钻、边界安全 | 数据 |
| **G5** | 增强直播变现 | 开播前中后全流程有工具支撑、复盘能指导下一场 | 直播 |
| **G6** | 保障系统健壮性 | 向后兼容、性能达标、异常不崩、多租户隔离无泄漏 | 组长 + 全员 |

## 三、评测标准（量化指标）

### 3.1 功能完成度（权重 35%）

| 等级 | 判定标准 |
|---|---|
| **完成（100%）** | 后端 service + 路由 + 前端入口 + 数据写入方 **四者齐备**，端到端可走通 |
| **半成品（50%）** | 后端通但前端无入口，或前端有但绑假数据 |
| **未完成（0%）** | 任一环节缺失导致用户实际用不了 |

> **红线**：本轮吸取教训——"后端修了前端没入口"直接判 **0 分**，不给半成品分。

计算式：`功能完成度 = Σ(各功能项得分) / (功能项总数 × 100%)`
**达标线：≥ 90%**

### 3.2 性能达标率（权重 15%）

| 场景 | 指标 | 达标阈值 |
|---|---|---|
| 单实体 CRUD 接口 | P95 响应 | ≤ 100 ms |
| 列表查询（分页 20 条） | P95 响应 | ≤ 300 ms |
| Analytics 聚合类接口 | P95 响应 | ≤ 800 ms |
| 应用冷启动到可交互 | 时长 | ≤ 3 s |
| 前端构建产物 | 主 bundle | ≤ 900 KB（gzip ≤ 250 KB）|
| 大数据量回归 | 1 万订单下聚合查询 | 不超时、不锁库 |

计算式：`性能达标率 = 达标项数 / 受测项总数`
**达标线：≥ 95%**

### 3.3 用户体验改善度（权重 20%）

| 维度 | 度量方式 | 达标 |
|---|---|---|
| 操作路径缩短 | 完成典型任务所需点击数（改造前 vs 后） | 平均减少 ≥ 30% |
| 空状态友好 | 所有列表/图表在无数据时有引导文案而非空白或崩溃 | 100% 覆盖 |
| 错误可理解 | 后端错误在前端有中文可读回显，不暴露堆栈 | 100% 覆盖 |
| 口径透明 | 每个指标旁有口径说明（tip/悬浮/脚注） | 100% 覆盖 |
| 异常主动性 | 关键异常（断货/超卖/合规风险/目标偏离）主动推送而非等用户查 | ≥ 5 类 |

### 3.4 数据可信度（权重 20%）

| 维度 | 达标 |
|---|---|
| 口径唯一性 | 同一指标全系统仅一处定义，无冲突实现 |
| 无空表 | 新增表均有真实写入方与前端触发入口 |
| 边界安全 | 所有比率类指标分母为 0 时返回 0 而非 NaN/Infinity |
| 可追溯 | 关键指标可下钻到明细记录 |
| 多租户隔离 | 100% 的 SQL 带 tenant_id 过滤，跨租户访问返回 404 |

### 3.5 向后兼容（权重 10%，**一票否决**）

| 检查项 | 达标 |
|---|---|
| 存量冒烟用例 | 原 51 项端到端用例 **必须全绿**，任一退化即整体不通过 |
| 类型检查 | 前后端 `tsc --noEmit` 零错误 |
| 构建 | `npm run build` 成功 |
| 数据库迁移 | 在已有数据的库上重复执行两次，均成功且数据无损 |
| 既有 API | 不删除、不改变已有端点的请求/响应结构（只允许增字段） |

### 3.6 综合评分

```
综合得分 = 功能完成度×0.35 + 性能达标率×0.15 + 体验改善度×0.20
         + 数据可信度×0.20 + 向后兼容×0.10
```

**验收线：综合 ≥ 85 分，且向后兼容项无任何失败。**

## 四、执行约束（硬性，违反即回退）

1. **架构不变**：在现有 Electron + React + Express + SQLite 架构上做增量，不重构、不换栈。
2. **向后兼容**：既有 API 只增不改不删；数据库只加表加列，不删列不改类型。
3. **迁移幂等**：所有 DDL 用 `CREATE TABLE IF NOT EXISTS` / `ALTER TABLE ADD COLUMN` 并容忍重复执行。
4. **多租户隔离**：任何新增 SQL 必须带 `tenant_id` 过滤，跨租户访问返回 404（不泄露资源存在性）。
5. **零新依赖**：不引入任何新的 npm 包，图表一律手写 SVG。
6. **离线优先**：不得依赖联网。需外部数据的场景，一律提供**手工录入 / 文件导入 / 沙箱示例数据**三选一，且沙箱数据必须显式标记。
7. **四件套齐备**：新功能必须同时交付 后端 service、路由、前端入口、数据写入方，缺一不算完成。
8. **共享文件单点修改**：多方共用文件由组长统一落笔。

## 五、验收流程

```
专家自测 → 交叉评审（非本域专家复核） → 数据专家口径审计
   → 组长集成（tsc + 冒烟 + 回归 + 构建） → 产出评测报告 → 提交私有仓
```

**仓库铁律**：源码只推 GitHub 私有仓 `kule-2025/vorzai`；
公共仓与 Gitee 仅存放安装包与 Release 资源，严禁源码。
