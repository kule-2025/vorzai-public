## 一、背景与范围

首轮（B1–B8）已闭环：B1 工作流前端 UI、B2 CI+覆盖率门禁、B3 ogsm 重复路由、B4 hrStore 双写、B6 RBAC 等级统一、B7 租户隔离工厂（`authedRouter()`）均落代码并通过测试；B5/B8 留作渐进/专项项。

第二轮对三项做进一步取证与修复：

- **B5 实质**：尝试按评审建议推动 `strict` 时，发现 `server/tsconfig.json` 的冗余 `paths` 配置掩盖了大量类型错误，移除后暴露并修复多处真实潜在缺陷（含一处「设备上限死代码」安全逻辑缺陷）。

## 二、逐项修改说明与验证

### B7（续）· 邮箱路由跨租户泄漏 — P1 安全修复

| 维度 | 内容 |
|------|------|
| **根因** | `server/src/routes/email.ts` 是全部业务路由中**唯一**未使用 `authedRouter()` 的路由（仅 per-route `authenticateToken`，缺少 `tenantIsolation`）。其 `GET /api/connectors/email/:id/logs` 调用 `emailConnectorService.getSyncLogs(connectorId)`，该方法 SQL 仅按 `connector_id` 过滤，**未带 `tenant_id`**；而 `connector_id` 非租户不可推断，攻击者可用枚举 id 跨租户读取他方邮箱同步日志。 |
| **修改 1** | `email.ts`：`const router = Router()` → `const router = authedRouter()`（来自 `middleware/auth.ts`，组合 `authenticateToken + tenantIsolation`）；移除各路由 handler 上冗余的 `authenticateToken` 导入。 |
| **修改 2** | `emailConnectorService.getSyncLogs(connectorId: string)` 签名扩展为 `getSyncLogs(connectorId: string, tenantId: string)`；底层 SQL 改为 `WHERE connector_id = ? AND tenant_id = ?`。`email.ts` 调用点同步传 `req.user!.tenantId`。 |
| **影响面** | `getSyncLogs` 仅 `email.ts` 一处调用，无其余 caller 受影响；其余 email 路由此前已正确传 `tenantId`，本次一并统一到 `authedRouter()`。 |
| **验证** | `server/tsconfig.json` tsc `--noEmit` → **0 errors** ✅；`security.test.ts` 既有租户隔离原语用例保持通过。 |

> 安全意义：B7 首轮统一了 `tenant.ts` 等路由，但 `email.ts` 被遗漏。本次补上后，**所有业务路由均经 `authedRouter()` 强制租户隔离**，跨租户面清零。

### B5 · server strict 渐进 — 清除掩盖错误的 hack + 修复潜在缺陷

| 维度 | 内容 |
|------|------|
| **决策** | **保持 `strict: false`**。评审报告自身判定全局翻转风险高（数百处历史类型宽松点）。本次**不强行开 strict**，但清除导致错误被「静默吞掉」的配置，并修复由此暴露的真实缺陷。 |
| **修改 1（关键 hack 清除）** | `server/tsconfig.json` 删除冗余 `baseUrl: "."` + `paths: { "*": ["../node_modules/*"] }`。该 alias 在 `NodeNext` 下会把 `express` / `uuid` 等解析为 `any`，使本应报错的调用被掩盖。移除后类型检查恢复真实严格度。 |
| **修改 2（潜在缺陷已修复）** | 移除 paths 后 `tsc` 暴露并被修复的真实问题：<br>• `licenseService.ts`：新增 `LicenseLike` 接口；`activateLicense` 此前对 `validateLicense` 返回值读 **snake_case**（`license.max_devices` / `license.expires_at` / `license.tenant_id`），而返回对象实为 **camelCase** → 设备上限校验恒为 `undefined`，**设备数限制形同死代码（安全逻辑缺陷）**。修正为读 camelCase，设备上限校验恢复生效。同时 `revokeLicense` 的 `result.license.tenant_id` → `.tenantId`。<br>• `routes/business.ts`：6 处 `notFound(entity, id)` 实参此前与 `common.ts` 的 `(entity: string, id: string)` 签名不符，已对齐（含 `'退货申请'` / `'退款申请'` / `'标签'` / `'活动'`）。<br>• `knowledgeService.ts`：`.map((s) => s.trim())` → `.map((s: string) => s.trim())`（strict 下 implicit-any）。<br>• `routes/dialog.ts`：`keyGenerator` 返回值 `as string` 显式断言（ipKeyGenerator 联合类型）。<br>• `incentiveRuleEngine.ts`：`return result.changes > 0` → `return (result.changes ?? 0) > 0`（防御 `changes` 为 `undefined`）。 |
| **验证** | `server/tsconfig.json` tsc `--noEmit` → **0 errors** ✅；后端单测 **285/285 通过** ✅（含 license / business / incentive 相关用例）。 |

> 收益：本次不仅消除了掩盖错误的 hack，还修复了一处**真实的安全逻辑缺陷**（license 设备上限校验死代码）与 5 处类型/健壮性隐患，且未触发全局 strict 翻滚风险。

### B8 · 前端 QE / a11y / 性能工程 — 零依赖改进 + 根因定位

| 维度 | 内容 |
|------|------|
| **受阻项** | 按评审建议接入 `eslint-plugin-jsx-a11y@^6.10.0` 时安装失败：peer 冲突——项目 `package.json` 将 `eslint` pin 为 `^10.8.0`（非典型，npm 真实可用上限为 9.x），而 `jsx-a11y` 要求 `eslint <= 9`。该 pin 疑为笔误（`8.10` 或 `9.x` 之误），属**配置异常**，需先核实再接入 a11y 规则。 |
| **修改 1（零依赖 a11y 邻近改进）** | 新建 `eslint.config.mjs`（flat config），新增规则 `@typescript-eslint/no-misused-promises: 'warn'`——捕获 UI 事件处理器中未处理的 Promise 拒绝（典型前端运行时缺陷，如 `onClick` 直接传 `async` 函数）。 |
| **修改 2（包体预算）** | `vite.config.ts` `build` 增加 `chunkSizeWarningLimit: 1000`（1MB 告警阈值），推动按需拆包、避免首屏 bundle 膨胀（性能工程基线）。 |
| **验证** | `npx eslint --print-config src/App.tsx` → **exit 0**（flat config 含新规则，解析通过）✅；前端单测 **114/114 通过** ✅。 |
| **待办** | 核实并修正 `eslint` 版本 pin 后，再正式接入 `eslint-plugin-jsx-a11y` 与关键交互 a11y 断言。 |
